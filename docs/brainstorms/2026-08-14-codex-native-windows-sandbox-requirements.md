# Codex Native Windows Sandbox Setup Requirements

**Date:** 2026-08-14

**Status:** Investigation and product recommendation

**Scope:** PwrAgent desktop integration with the Codex native Windows sandbox

**Out of scope:** PR #1598, changing a Windows machine during this investigation,
and reading Codex-owned rollout, session, or sqlite storage

## Recommendation

PwrAgent should add a small, capability-gated Windows sandbox control plane for
the **active Codex profile**. It should:

1. query the Codex App Server's read-only `windowsSandbox/readiness` method;
2. combine readiness with `config/read`, `configRequirements/read`, the App
   Server initialize result, and setup notifications;
3. show the resulting status under **Settings → AI Providers → Codex → Windows
   sandbox**;
4. show one durable, deduplicated warning when native Windows sandboxing is not
   configured or needs an update, with an action that opens that settings
   section;
5. run `windowsSandbox/setupStart` only after the operator explicitly chooses a
   mode and confirms the OS-changing/UAC flow;
6. recommend elevated mode, retain unelevated mode as an explicitly described
   weaker fallback, and never silently choose it;
7. treat successful setup as **restart required** until a new Codex App Server
   process proves the resulting configuration is ready; and
8. intercept `/setup-default-sandbox` as PwrAgent UI navigation/setup intent,
   not send it to the model as prompt text.

PwrAgent must not auto-run setup, elevate the whole app, rewrite Codex config
directly, silently fall back to full access, or weaken a managed policy. Codex
must remain the source of truth for each profile's sandbox mode and setup state.

## What was inspected

This investigation read:

- repository and desktop-app guidance;
- the current access-mode and permission-state-machine design records;
- the Codex App Server client and compatibility layer;
- backend command discovery and composer slash-command execution;
- the desktop settings IPC/preload/API bridge;
- AI Providers settings and Codex profile selection;
- application notice/toast state and settings deep-linking; and
- the current Codex App Server JSON schema generated by `codex-cli 0.146.1`.

It also used the official Codex manual and the upstream `openai/codex` source at
commit `3360f4a909a920d2e534a63c508d98e91fe6655a`. It did **not** inspect any
Codex-owned session JSONL, rollout, or sqlite file and did not invoke Windows
sandbox setup.

## Evidence and confidence

### Documented facts

The current [Codex Windows sandbox documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox.md)
documents two native Windows implementations:

- `windows.sandbox = "elevated"` is the preferred implementation. Setup uses
  dedicated lower-privilege sandbox users, filesystem boundaries, firewall
  rules, and local policy changes.
- `windows.sandbox = "unelevated"` is a fallback that uses a restricted token,
  ACL boundaries, and environment-level offline controls. It provides weaker
  isolation.
- Both use a private desktop by default unless
  `windows.sandbox_private_desktop = false` is configured.
- Managed requirements may restrict allowed implementations through
  `allowed_sandbox_implementations`.

The [Codex CLI command documentation](https://learn.chatgpt.com/docs/developer-commands?surface=cli)
describes `/setup-default-sandbox` as a Windows-only TUI command shown when
Codex is using the degraded restricted-token sandbox. It enters an administrator
setup flow for the elevated sandbox and selects the automatic approval preset.
`/sandbox-add-read-dir ABSOLUTE_PATH` grants an additional read directory for
the current native-Windows CLI session only.

The [Codex App Server documentation](https://learn.chatgpt.com/docs/app-server.md)
documents `windowsSandbox/setupStart`:

```text
request:  { mode: "elevated" | "unelevated", cwd?: absolute path }
response: { started: true }
event:    windowsSandbox/setupCompleted
          { mode, success, error? }
```

The response only acknowledges that background setup started. Completion is an
asynchronous notification.

The generated 0.146.1 App Server schema additionally exposes a read-only method
that the prose App Server guide does not currently list:

```text
windowsSandbox/readiness ->
  { status: "ready" | "notConfigured" | "updateRequired" }
```

The same schema defines a `windows/worldWritableWarning` notification with
sample paths, an extra-path count, and a `failedScan` flag. Codex describes
these paths as unsafe because folders writable by Everyone cannot be protected
by the sandbox.

The [Codex security documentation](https://learn.chatgpt.com/docs/agent-approvals-security)
describes the automatic/default access preset as `workspace-write` plus
`on-request`: workspace reads and edits should ordinarily proceed automatically,
while actions outside the workspace or needing network access request approval.

### Facts established from upstream source

The App Server's [Windows sandbox request processor](https://github.com/openai/codex/blob/3360f4a909a920d2e534a63c508d98e91fe6655a/codex-rs/app-server/src/request_processors/windows_sandbox_processor.rs)
maps readiness as follows:

| Effective Codex state | Readiness |
|---|---|
| Windows sandbox disabled | `notConfigured` |
| Restricted-token/unelevated implementation | `ready` |
| Elevated implementation with current setup | `ready` |
| Elevated selected but setup missing or stale | `updateRequired` |

Before acknowledging setup, the processor loads configuration for the supplied
working directory and rejects a mode disallowed by managed requirements. It
then runs setup asynchronously and emits `windowsSandbox/setupCompleted`.

The upstream [Windows sandbox configuration implementation](https://github.com/openai/codex/blob/3360f4a909a920d2e534a63c508d98e91fe6655a/codex-rs/core/src/windows_sandbox.rs)
runs the requested preflight and, on success, persists the selected mode into
the active Codex configuration with Codex's own config editor. It also removes
legacy Windows-sandbox feature keys. PwrAgent therefore should not perform a
second `config/value/write` for the mode.

The upstream [patch-safety decision](https://github.com/openai/codex/blob/3360f4a909a920d2e534a63c508d98e91fe6655a/codex-rs/core/src/safety.rs)
only auto-approves an in-workspace patch when a real platform sandbox can
enforce the writable-root boundary. On native Windows, no platform patch
sandbox is available when the Windows sandbox level is disabled. Under
`on-request`, that path returns an approval request even when the proposed patch
is inside the workspace.

### Inferences that still require a Windows-lab check

The following conclusions are strongly supported but are not a stable public
protocol contract:

- A missing `[windows]` selection in the reproduced active profile resolves to
  disabled native Windows sandboxing. That exactly matches the upstream reason
  an in-workspace file-change request asks for approval. Project trust does not
  replace the platform sandbox and is orthogonal to this check.
- Command execution and patch application can behave differently while the
  sandbox is unconfigured. The command executor has a restricted-token Windows
  fallback, while the patch-safety path refuses to claim safe containment
  without a configured platform sandbox.
- After successful App Server setup, the current App Server process may retain
  its startup `Config` in memory. The setup processor persists config and emits
  completion but does not visibly reload that process's config. The TUI has
  separate code that updates its in-memory state. PwrAgent should consequently
  show **Restart required** until a fresh App Server reports `ready`, rather
  than optimistically changing the current runtime state.

A conclusive diagnosis on the original VM should record, through the protocol
only, the initialize platform fields, `windowsSandbox/readiness`, effective
`config/read` output, `configRequirements/read`, and the approval request method
and reason. The available repro is consistent with this cause but did not
capture all of those values together.

## Current PwrAgent behavior and gaps

### Access mode is being passed correctly

PwrAgent Default Access explicitly passes `approval_policy = "on-request"` and
`sandbox_mode = "workspace-write"` at turn start. The established permission
state machine deliberately does not trust provider defaults. The observed
approval is therefore not evidence that PwrAgent accidentally selected Read
Only or Full Access.

`workspace-write` is a requested policy, not an implementation of a Windows
security boundary. If the active Codex profile has no native Windows sandbox,
Codex cannot safely honor the usual no-prompt workspace-patch behavior.

### App Server adapter

`apps/desktop/src/main/codex-app-server/client.ts` has generic JSON-RPC request
support plus typed wrappers for several config operations, but no Windows
sandbox wrapper. Its known-notification set does not contain
`windowsSandbox/setupCompleted` or `windows/worldWritableWarning`; those
notifications are currently logged as unhandled before being forwarded through
the generic notification path.

The initialize response already retains `platformFamily`, `platformOs`, and
supported methods. Those should gate native-Windows UI and capability checks.
`process.platform === "win32"` alone is not enough to distinguish the actual
Codex execution environment from WSL, a remote backend, or a future bridge.

### Slash commands

PwrAgent's command surface is a combination of:

- local renderer commands such as `/review` and `/mcp`;
- a synthesized `/compact` command when `thread/compact/start` is available;
- Codex skills; and
- ACP-advertised commands.

The App Server does not advertise its TUI's built-in slash commands and has no
generic “execute slash command” method. An unhandled command is composer text
and can be sent to the model. Merely adding `/setup-default-sandbox` to command
discovery would therefore be incorrect.

PwrAgent should synthesize `/setup-default-sandbox` only when the active backend
is Codex, the initialize result says native Windows, and readiness/setup methods
are supported. Composer execution must intercept it and open the Windows
sandbox settings/setup confirmation. It must never begin privileged setup as a
side effect of typing or selecting the command.

PwrAgent should not expose `/sandbox-add-read-dir` yet. Its documented lifetime
is the current CLI session, and there is no equivalent App Server request in the
current schema. Sending it as model text or emulating it with config changes
would misrepresent its security semantics.

### Profiles and settings lifecycle

Settings → AI Providers already supports Codex binary discovery, connection
testing, and multiple auth/config profiles. The desktop settings service fixes
`startupCodexHome` when PwrAgent starts and injects that `CODEX_HOME` into the
long-lived Codex App Server. Changing the selected profile is explicitly a
next-launch operation.

The Windows sandbox section must therefore be labeled with the active profile
name and home. In phase 1:

- status and setup operate only on the active/startup profile;
- selecting a different profile shows “Restart PwrAgent to inspect or configure
  this profile”;
- PwrAgent does not start an extra App Server against an inactive profile; and
- status is keyed by canonical Codex home so one profile's result cannot leak
  into another profile's UI.

This constraint is especially important because elevated setup changes OS
state as well as one profile's config. Competing clients, multiple windows, or
an ambiguous profile label are unacceptable for a privileged operation.

## Proposed UX

### Settings → AI Providers → Codex → Windows sandbox

Show this section only when the active Codex App Server reports native Windows.
Do not warn or show setup controls on macOS, Linux, or WSL. If the installed
Codex is too old to advertise the methods, show a neutral “Unavailable in this
Codex version” row with an upgrade action or guidance; do not call it
`notConfigured`.

The section should contain:

- **Profile:** active Codex profile and its home path;
- **Status:** Checking, Ready, Not configured, Update required, Setup running,
  Restart required, Failed, Unsupported, or Unknown;
- **Mode:** Elevated (recommended), Unelevated (weaker), None, or Unknown;
- **Managed policy:** allowed modes, when requirements restrict them;
- **Private desktop:** a read-only summary in the first release rather than a
  new toggle;
- **Explanation:** Default Access needs a native Windows boundary to make
  ordinary workspace edits without avoidable approval prompts;
- **Actions:** Set up elevated sandbox, use unelevated fallback, retry, refresh,
  or restart PwrAgent, depending on state; and
- **World-writable warning:** sampled affected paths and scan-failure state when
  Codex reports them, without attempting to change ACLs.

Use existing `SettingsSection`, field, status-chip, and warning-token primitives.
Status must have text/icon semantics and not rely on color alone.

Suggested copy:

> **Windows sandbox not configured**
>
> Default Access cannot reliably contain file changes to this workspace until
> Codex's native Windows sandbox is configured. Setup may request administrator
> approval and change local users, firewall rules, and security policy.

For the fallback:

> **Use unelevated sandbox**
>
> This avoids administrator setup but provides weaker isolation. Choose it only
> when elevated setup is unavailable or blocked by your organization's policy.

The elevated action must open a confirmation that names the active profile,
mode, and working directory, explains the OS changes and UAC prompt, and makes
cancel the safe default. PwrAgent itself should remain unelevated.

### Warning behavior

Show a single durable app notice only when all of these are true:

- the active backend is Codex running natively on Windows;
- the readiness method is supported;
- readiness is `notConfigured` or `updateRequired`; and
- the operator is using, or is about to use, an approval mode that expects
  sandboxed automatic workspace work.

The notice action is **Review sandbox**, which opens Settings → AI Providers →
Codex and focuses the Windows sandbox section. Setup must require a second,
explicit choice there.

Deduplicate by active canonical `CODEX_HOME` plus readiness state. Dismissal may
last for the current app session, but a changed status, changed active profile,
or later app launch may surface it once again. Recheck at app-server
initialization, when the section opens, after setup completion, and on a
cooled-down window-focus event. Do not check or toast per command, turn, item,
or streamed event.

A world-writable warning is a separate, higher-specificity security notice. It
should be durable and deduplicated by active profile and a stable summary, avoid
including sensitive path data in telemetry, and link to the same settings
section. PwrAgent must not auto-edit ACLs.

## Status model

PwrAgent needs a normalized, renderer-safe state rather than exposing raw JSON:

| PwrAgent state | Evidence | Primary action |
|---|---|---|
| `unsupported` | not native Windows or methods absent | none or upgrade Codex |
| `checking` | probe in flight | none |
| `notConfigured` | readiness says so | set up elevated; offer unelevated fallback |
| `readyElevated` | ready plus effective elevated config | none |
| `readyUnelevated` | ready plus effective unelevated config | offer optional upgrade to elevated |
| `updateRequired` | readiness says so | rerun setup for configured/allowed mode |
| `setupRunning` | setup ACK plus pending completion | wait; prevent duplicate setup |
| `restartRequired` | successful completion, current process not re-proven ready | restart PwrAgent |
| `failed` | structured request failure or unsuccessful completion | explain, retry, preserve prior state |
| `unknown` | contradictory/malformed/transient evidence | refresh, diagnostics, no security claim |

Readiness alone does not identify the mode. The service should read effective
config through `config/read` and managed constraints through
`configRequirements/read`. If mode and readiness conflict, show `unknown` or
`updateRequired`; never infer the stronger mode.

## Proposed data flow

```text
PwrAgent startup / Settings open / cooled-down focus
  → active Codex App Server initialize result
  → capability + native-Windows gate
  → windowsSandbox/readiness (read-only)
  → config/read + configRequirements/read
  → main-process normalized active-profile snapshot
  → typed IPC snapshot/event
  → AI Providers section + deduplicated app notice

Operator chooses setup
  → settings section confirmation
  → main validates active profile, native Windows, policy, and setup mutex
  → windowsSandbox/setupStart({ mode, cwd })
  → { started: true }
  → setupRunning UI; Codex owns UAC and OS setup
  → windowsSandbox/setupCompleted({ mode, success, error })
  → failure: preserve honest state and allow retry
  → success: restartRequired
  → PwrAgent restart starts Codex with the same CODEX_HOME
  → fresh readiness/config probe must prove ready and mode
```

The main-process service is authoritative only for the current process's
observation. Codex configuration remains authoritative on disk and is accessed
through the App Server protocol.

## Security and lifecycle requirements

1. **No implicit privilege.** Never invoke setup at startup, on first turn, on
   notice click, or on slash-command completion without an explicit confirmation.
2. **No silent weakening.** Never select unelevated because elevated setup fails,
   UAC is declined, or a timeout fires. Explain the fallback and require choice.
3. **No whole-app elevation.** Let Codex own the narrow UAC/helper flow. Running
   the Electron app elevated would widen the blast radius of every renderer and
   integration.
4. **No silent full access.** Setup failure must not change PwrAgent's access
   mode or retry a turn with `danger-full-access`.
5. **Honor managed requirements.** Disable disallowed modes and explain that
   policy, using `configRequirements/read`; do not offer a bypass.
6. **Identify the target.** Bind every operation to the active canonical
   `CODEX_HOME`, selected mode, and a validated absolute `cwd`.
7. **Serialize setup.** One setup attempt per active App Server/profile. Multiple
   windows receive the same progress snapshot and cannot start duplicates.
8. **Do not assume timeout means rollback.** Setup is asynchronous and can
   outlive a renderer. A missing completion notification is unknown, not proof
   of failure; require refresh/restart and preserve conservative copy.
9. **Treat partial OS setup as Codex-owned recovery.** Surface the returned error
   and official remediation, but do not remove users, groups, firewall rules,
   ACLs, or policy entries.
10. **Keep paths private.** Redact setup errors for renderer/log transport as
    appropriate. Do not send sampled world-writable paths to telemetry.
11. **Do not inspect Codex storage.** Diagnostics may explain how an operator can
    find the official sandbox log, but PwrAgent must not ingest Codex's private
    files to manufacture status.
12. **Do not configure remote owners.** A local viewer of a federated Windows
    thread cannot configure the owning instance. Only that instance's active
    settings surface may run setup.
13. **Expect enterprise failures.** UAC cancellation, blocked local-user/group
    creation, blocked firewall or policy changes, missing logon rights (including
    Windows error 1385), and world-writable directories need actionable but
    non-destructive error handling.
14. **Preserve packaged-build behavior.** Exercise the shipped Codex binary
    selection, selected profile environment, UAC behavior, app restart, and
    update/version compatibility in a packaged Windows build.

## Protocol gaps to raise upstream

A sound first release is possible, but these gaps limit fidelity:

1. `windowsSandbox/readiness` and its exact status semantics are present in the
   generated schema/source but absent from the prose App Server guide.
2. Readiness does not include the effective mode, why setup is degraded/stale,
   whether setup is running, a last failure, or whether the current process must
   restart.
3. There is no documented App Server config-reload or self-restart operation.
   It is unclear whether a successful setup can safely update the current
   process's runtime policy without restart.
4. Setup has only started/completed signals: no structured progress,
   cancellation, recovery state, or structured error codes.
5. `windows/worldWritableWarning` is event-only; there is no read-only snapshot
   to recover a warning missed before a renderer subscribed.
6. There is no App Server equivalent of `/sandbox-add-read-dir`.
7. There is no App Server discovery/execution contract for built-in Codex TUI
   slash commands. PwrAgent must explicitly map supported operations.
8. The relationship between the optional setup `cwd`, config-layer resolution,
   and profile-global persisted mode deserves an explicit protocol guarantee.

Until gaps 2 and 3 are resolved, PwrAgent should conservatively require restart
after successful setup. Until gap 5 is resolved, the world-writable warning can
only be best-effort during the lifetime of the active App Server.

The smallest safe prerequisite is a typed, read-only
`windowsSandbox/readiness` wrapper plus typed parsing for the two Windows
notifications. That would remove the current “unhandled notification” blind
spot without changing Windows state. It should be implemented as the first
slice, but it was not necessary to implement it to establish this design.

## Phased implementation plan

### Phase 0: Protocol contract and upstream clarification

- Pin schema fixtures for the installed/supported Codex versions.
- Add compatibility probes for readiness and setup methods.
- Ask upstream to document readiness, runtime reload/restart semantics, and the
  world-writable snapshot gap.
- Validate the disabled-sandbox approval explanation through a protocol capture
  in the operator's Windows lab.

Exit criterion: PwrAgent can distinguish unsupported, not configured, ready,
and update required without filesystem inspection or state changes.

### Phase 1: Read-only visibility

- Add the main-process status service and typed bridge.
- Add the active-profile Windows sandbox settings section.
- Add the deduplicated warning/deep-link.
- Surface world-writable notifications conservatively.
- Do not expose setup actions yet if restart/runtime semantics remain untested.

Exit criterion: a native-Windows operator can understand the active profile's
state and remediation path, while non-Windows and old-Codex users see no false
warning.

### Phase 2: Explicit setup

- Add setup confirmation and elevated/unelevated controls.
- Enforce managed requirements and one-at-a-time setup.
- Handle asynchronous completion, UAC cancellation, failure, missing completion,
  and app/window lifecycle.
- Show restart required after success and re-probe after restart.
- Add `/setup-default-sandbox` as a local navigation/setup action.

Exit criterion: an authorized Windows operator can configure either allowed
mode for the active profile, and PwrAgent never claims success before a fresh
App Server proves it.

### Phase 3: Fidelity improvements after upstream support

- Replace conservative restart behavior if Codex adds a documented reload
  contract.
- Add structured progress/recovery and a read-only world-writable snapshot.
- Consider explicit inactive-profile management only if App Server gains a safe,
  profile-addressed management contract.
- Consider `/sandbox-add-read-dir` only when App Server exposes matching
  session-scoped semantics.

## Test plan

### Unit and contract tests

- Parse all readiness values and reject unknown/malformed responses safely.
- Treat missing methods as unsupported, not not-configured.
- Merge readiness, config mode, managed requirements, platform, and completion
  into every normalized state.
- Verify `ready` never becomes “Elevated” without effective config evidence.
- Verify successful completion becomes restart-required until a fresh probe.
- Verify setup request rejection, `{ started: false }`, completion failure,
  missing completion, UAC-cancel text, and redacted errors.
- Verify setup serialization and multi-window subscribers.
- Verify profile-home changes invalidate cached state and dismissed notices.
- Verify world-writable warning samples/count/failed-scan handling.
- Verify no setup path calls `config/value/write` for the selected mode.

### Renderer tests

- Hide the section and notice on non-Windows/WSL and remote-owner contexts.
- Render unsupported, not configured, elevated ready, unelevated ready, update
  required, running, failed, and restart-required states.
- Disable modes prohibited by managed requirements.
- Show active profile identity and restart guidance for a newly selected profile.
- Require confirmation before setup; notice click only navigates.
- Deduplicate dismissal and resurface on meaningful state/profile change.
- Verify `/setup-default-sandbox` opens the UI and never calls `startTurn` or
  `steerTurn`.
- Verify `/sandbox-add-read-dir` is not advertised.

### Replay-backed desktop E2E

Use replay fixtures for each readiness/config/notification combination to test
the Settings deep-link, notice behavior, setup confirmation, async success and
failure, renderer restart-required state, and multiple-window updates. Replay
tests must not invoke UAC or mutate the host.

### Operator-provided Windows lab

Repository guidance requires an operator-provided lab pointer before headed
desktop E2E. In an isolated native Windows VM, with explicit authorization for
each state-changing case:

1. Start a fresh Codex profile with no `[windows]` selection. Record
   initialization, readiness, effective config, requirements, and an
   in-workspace file-change approval through the protocol.
2. Authorize elevated setup from a non-elevated PwrAgent process. Verify the UAC
   experience, completion event, persisted mode through `config/read`, restart
   requirement, and `ready` after restart.
3. Under Default Access after restart, verify an ordinary in-workspace file
   creation does not ask, while an outside-workspace write and network action
   still follow their approval policy.
4. Test explicitly authorized unelevated setup and verify weaker-mode copy.
5. Test UAC decline, setup failure, retry, blocked local-user/group creation,
   blocked firewall/policy changes, missing logon rights/error 1385, and
   world-writable directories.
6. Test `updateRequired` using a safe disposable VM/profile fixture.
7. Test managed allowed-mode restrictions.
8. Test two Codex profiles with different modes and ensure restart/profile
   isolation.
9. Test a packaged PwrAgent build, Codex upgrade/downgrade capability changes,
   app quit during setup, multiple windows, and restart recovery.
10. Confirm WSL and remote/federated Windows threads do not expose a local setup
    action for the wrong runtime.

No Windows setup case should run on an operator machine without explicit
authorization. Disposable snapshots should bracket all privileged and failure
tests.

## Decision summary

The live repro is best explained by an unconfigured native Windows sandbox, not
by workspace trust or PwrAgent's Default Access mapping. Codex deliberately asks
for an in-workspace patch when it cannot enforce the Windows boundary. PwrAgent
currently has all the architectural pieces needed to expose this honestly, but
it does not call the readiness/setup protocol, does not type the relevant
notifications, and cannot execute TUI slash commands generically.

The right product response is visible, profile-scoped status plus an explicit
Codex-owned setup flow. It is not an automatic privilege flow, an approval
bypass, or a PwrAgent-owned sandbox implementation.
