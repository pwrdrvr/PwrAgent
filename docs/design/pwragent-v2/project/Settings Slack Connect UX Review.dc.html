01 — The core problem

The most important thing the button does is the one thing it never shows you

Pressing Update existing Slack app does two things: it opens api.slack.com/apps in the browser, and it writes the whole PwrAgent app manifest to the clipboard. The manifest is the task — everything after this point is paste-and-save. It is also the half of the action with no visible consequence.

The browser jumping to the foreground is unmissable. The clipboard write produces nothing at the point of action: no label change, no icon, no colour, no motion, no sound. The only evidence is a sentence in 12px muted text that renders below a three-item numbered list and a paragraph about workspace admins — a measured 119 px and five lines of unrelated copy beneath the button that caused it, and often below the fold of the settings pane.

“It's not really clear that we copied the manifest to the clipboard, and I don't think we give the user a button to copy it again. Clicking ‘update app’ just does copy it — but it's so confusing, you have to read the paragraph below to know that it put something on the clipboard.”

02 — Findings

Eleven findings, ranked

Each finding names the evidence it rests on. References are against branch HEAD.

Blocking
B1The clipboard write has no acknowledgement at the point of action

All three actions write to the clipboard on some path — the manifest on update, the manifest on an oversized create URL, the create link on copy — and all three report it the same way: by replacing a paragraph at the bottom of the card. The button itself never changes. A clipboard write is invisible by nature, so the acknowledgement has to be attached to the control that caused it; a sentence rendered after two intervening blocks is not attached to anything.

Fix: acknowledge at the control. Swap the label to Copied for ~1.5 s, the way the pairing row four fields down this same panel already does.

Evidence — SlackConnectCard.tsx: copyText(result.manifestJson, …) followed only by setStatus(…). Rendered status sits after .slack-connect__checklist and .slack-connect__admin; measured 12px / #b8b0a5, no border, no fill, no icon, 119 px below the pressed button.

B2The manifest cannot be copied again without re-opening the browser

The update handler hard-codes { mode: "update", open: true }, so copying the manifest and launching a browser tab are one indivisible action. The manifest is never rendered, never stored on screen, and has no copy control of its own — the clipboard is the only place it exists. Every remaining step of the task happens in a browser, where the user will plausibly copy something else. Recovery costs a duplicate tab, and nothing on the card tells them that pressing the button again is the recovery.

Fix: separate copy the manifest from open Slack. A persistent, idempotent Copy manifest that never navigates is the single highest-value change on this card.

Evidence — SlackConnectCard.tsx, updateExisting(). No render path displays result.manifestJson.

B3The progress state appears on a button the user did not press

One busy flag is shared by all three actions, and only the first button renders it: {busy ? "Opening…" : "Create Slack app"}. Press Update existing Slack app and the Create Slack app button changes to “Opening…” while the pressed button simply greys out. The feedback lands on the wrong control — and on a slow clipboard or a slow shell open, it reads as though the app started creating a new Slack app.

Fix: track which action is in flight, not whether any action is; render the pending label on the pressed button.

Evidence — measured in the harness with a 2.5 s stubbed openSlackCreateApp: after clicking Update existing Slack app, buttons[0].innerText === "Opening…".

Should fix
S1Three buttons, no hierarchy

The three controls are visually interchangeable. Measured: identical color (#f7f3eb), identical border (rgba(247,243,235,0.1)), identical weight (400) and size (16px). Only the background differs — #101010 against transparent, on a #0a0a0a card, a step small enough to disappear under glare. In the light theme they are effectively identical. The design system ships .button--primary (amber border, --bg-row-active fill, --accent-bright text) and this card, the entry point to the whole Slack integration, does not use it.

Fix: one primary. .button--primary on the action that fits the card's current state.

Evidence — getComputedStyle on all three buttons, dark and light.

S2Two different jobs share one row

Create Slack app and Copy Create Slack app link are one job with two delivery modes — stand up a new app yourself, or hand the link to an admin who can. Update existing Slack app is a different job for a different person at a different time: someone already connected, returning because PwrAgent shipped a new manifest. Sharing a row at equal weight taxes both audiences — the first-run user reads and discards a third option, and the returning user hunts for maintenance inside a card titled “Connect Slack” whose instructions open with “In the new app…”.

Fix: give the update path its own block, its own label and its own steps.

S3The checklist contradicts the update path once it runs

The <ol> is create-only and static. After an update it still reads “In the new app, click Install to Workspace and Allow” — there is no new app, and re-installing is not part of a manifest update. Two sets of instructions for two different tasks are on screen at once, and the wrong one is the one with numbers.

Fix: make the step list belong to the path in play.

S4The update procedure is prose where the create procedure is a list

“Choose your existing PwrAgent app, open App Manifest, replace the manifest, and save changes” is four sequential UI actions in one sentence, in muted 12px, delivered after the browser has taken focus. The create path gets a numbered list for the same kind of content. The user returning from Slack has to re-parse a sentence to find their place.

Fix: same treatment as create — discrete, checkable steps.

S5Nothing tells an operator their Slack app needs updating

This control exists because the manifest changed — Agent Sessions events and the v2 Agent View. An operator running a working v1 app gets no signal: no stored manifest version, no comparison, no chip, no notice. The button only helps someone who already knows they need it, which is close to nobody. The section header already renders a chip (Not configured) and could carry this.

Fix: record the manifest version applied and surface drift on the section header, so the button appears when it is the answer to a question the user actually has.

Polish
P1The intro duplicates the field label's own subtitle

The field sub reads “Create a customer-owned Slack app from PwrAgent's official manifest, then paste the two tokens.” The card intro, 24 px to its right, opens “Create a customer-owned Slack app from PwrAgent's official manifest.” Eleven identical words, side by side. The second sentence — the Socket Mode / no-client-secret claim — is the only part carrying information.

P2Three labels sharing “Slack app” cannot be scanned

Create Slack app / Copy Create Slack app link / Update existing Slack app. The distinguishing word is first in one, third in another, first in the third, and every label must be read to its end. “Copy Create” also reads as two verbs in a row.

P3The shared .button primitive carries no font-size, so these are the loudest text on the panel

A survey of every button rendered in the Slack panel found six type scales. .button declares min-height and padding but no font-size, so it inherits the 16px UA default — while the panel's own chrome buttons (Collapse all, Expand all) set 11px/600, segmented options set 12px/650, and every body string in the card is 12px. The result: the three Slack buttons are the largest text in the panel body, six pixels off the panel's <h1>, carrying no hierarchy among themselves. This is a shell-level gap, not something the branch introduced — but the card is where it shows.

Evidence — scales found: 16/400 (.button), 13/650, 12/650, 12/600, 12/500, 11/600, 11/500.

Holds up
✓Accessibility, semantics and reflow

axe-core reports zero violations across WCAG 2.0/2.1/2.2 A and AA, in both themes, at 1280 px. The controls are real <button> elements; status uses role="status" and errors role="alert", so the acknowledgement B1 describes is announced to a screen reader — the gap is visual only. .slack-connect__actions wraps cleanly at 900 px with no overlap or clipping.

04 — Recommendation

Ship A now; B is where it wants to end up

Direction A clears both blocking findings and four others without inventing a single new pattern — it reuses the copy row that already exists twice in this codebase. It is the change that should land with this branch. B needs the app to remember which manifest version a workspace is on, which is real work and a separate change; it is worth doing, because until something detects drift the update button answers a question nobody knew to ask (S5). C is the ceiling if this flow ever becomes a first-run wizard surface.

One thing worth deciding before any of it. Every other clipboard write in this card is silent too — the create link, and the oversized-URL fallback that quietly copies the whole manifest instead of opening a browser. Whatever acknowledgement pattern lands, apply it to all three paths, or the card will teach the user that a press sometimes copies and sometimes does not.
