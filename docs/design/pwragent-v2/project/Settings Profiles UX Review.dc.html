Profiles pane — UX review

The docs screenshot recapture caught the Delete button running off the right edge of the pane. That clip is a symptom: the profile row is 1261 px wide at every window size, and each row is 219 px tall for four facts. This page measures the pane as built, then proposes a three-line card.

01

What the recapture caught

Numbers below are measured in headless Chromium against the real app.css with the real ProfilesSettings component mounted, at the docs capture size (1440 × 900).

DefectMeasuredCause
Actions clipped Delete 69 px wide
5 px inside the clip		 .settings-section__body-clip is display:grid; overflow:hidden with no grid-template-columns. Its implicit auto track floors at the row's min-content width, so the row is 1261 px at 1440, 1200, 1000 and 880 px windows alike — and the clip cuts whatever hangs past 1202 px.
Buttons oversized 16 px text
in a 12 px pane		 button { font: inherit } plus no root font-size means every .button lands at the 16 px UA default. Sibling settings buttons all set one (.settings-section-controls__button is 11 px); .settings-profile-row__button never did.
Rows are tall 219 px per row
698 px for 3		 Each row stacks name, path, timestamp, a section label, a full-width select, a nested detail card, and a helper sentence — eight stacked blocks for what is really four facts.
Card inside a card 52 px detail box The Codex detail box repeats the name already shown in the select above it, on the same elevation as its parent — so the nesting reads flat and the repetition reads like two different things.
Control out of scale 778 px select The auth select stretches the full body width for a 24-character value, which makes it the loudest element in a row about something else.
Repeated boilerplate × 1 per profile "Applies the next time this PwrAgent profile launches." is a property of the feature, not of a profile, but it is rendered once per row.
Status far from subject ≈ 700 px apart Active and Startup default sit at the far right of the row, separated from the profile name they qualify by the whole body column.

The eye has nothing to follow

Name, path, timestamp, label, control, nested card and helper are all left-aligned at the same x, in three type sizes that differ by 1.5 px. There is no scan edge and no rhythm, so finding "which profile am I looking at" means reading every line. That is the "unreadable" complaint, and it is a hierarchy problem rather than a spacing one.

03

Proposed — a three-line profile card

One card, three lines, in the order an operator asks the questions: which profile (name + state + what I can do to it), where and when (path + last used), which Codex identity it runs as. The nested detail box is gone; its path and chips fold into the Codex line beside the control they describe. The repeated helper sentence moves up into the section description, where it belongs once.

  • Name and state travel together. The two chips move next to the name, so "which one is live" is answered in the first 200 px of the card.
  • Actions shrink to the pane's scale. 28 px tall, 12 px label — the same weight as everything else in Settings instead of the 16 px UA default. Delete keeps its danger colour and gains a gap so it is not a neighbour of Open.
  • Paths get tildified, and truncate in the middle. tildifyPath() already ships in lib/tildify-path.ts. Splitting at the last separator and pinning the tail keeps the identifying segment — /default, /.codex — on screen, which a plain text-overflow: ellipsis is guaranteed to eat first. The full value stays on the title.
  • The Codex line is one line. Label, a 260 px control, the codex home, and the status chips. The chips right-align, so no auth and missing form a status column the eye can run down instead of hunting each nested box.
  • Everything can shrink. Fixing the grid track and giving each flex child min-width: 0 is what makes the row track the window instead of its own content.

05

The one open call

Everything above is settled by the measurements. This one is a taste call, so it is worth a look before it ships.

A · Three buttons, Delete set apart recommended

Keep all three actions visible; give Delete danger colour and an extra 6 px gap so it is not adjacent to Open. The confirm dialog stays.

  • No new component, no new keyboard model.
  • Every action is one click and is reachable by Tab in reading order.
  • Costs ~215 px of the head row; wraps below the name under ~640 px.

B · Two buttons + a ⋯ menu

Use on startup and Open stay; Delete moves into a per-card overflow menu.

  • The only irreversible action on the pane stops being a misclick neighbour.
  • Head row drops to ~180 px, so it wraps later.
  • Adds a menu + focus trap per card, and hides a discoverable action behind a glyph.

Not in scope

The delete confirm dialog, the create-profile dialog, and the Codex profile creation flow are unchanged. The grid-track fix lands on .settings-section__body-clip, which every settings pane shares — it can only make an over-wide panel shrink to fit where it previously overflowed into overflow: hidden, so it is a strict improvement everywhere.
