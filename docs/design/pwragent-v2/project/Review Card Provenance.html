R3Which PR the row is allowed to name

The row names the PR open on the branch the reviewed workspace had checked out — not the thread's PRs, not the repository's. A checked-out branch carrying a PR is a strong signal that the PR is what was reviewed; nothing else in the thread is evidence about this diff.
  1. Take the branch checked out in the reviewed workspace — LinkedDirectorySummary.gitBranch for the project the operator picked, never the thread's ambient branch.
  2. Match it against PrSummary.headRefName, narrowed by linkedDirectoryPaths so a branch name that exists in two of the thread's repos can't cross over.
  3. At most one chip. No match is “no PR at review time”; no branch to match on is no chip at all. Never a list.

R4Confidence — say what the number is about, or print none

REVIEW_OUTPUT_INSTRUCTIONS in managed-review.ts asks for overall_confidence_score and never defines it. overall_correctness gets an enum; this gets nothing. The badge then prints it with no referent, so “98% confidence” reads either as “the code is 98% fine” or “I'm 98% sure of my verdict” — and today both are guesses.

Three specifics. One: the example line in that prompt is literally "overall_confidence_score":0.0 — a value a weaker model copies straight through, producing a 0% confidence badge next to Patch correct. Two: Codex's native review/start supplies its own number under Codex's own meaning — confidence in the verdict — while managed reviews on every other backend run the undefined prompt. Same badge, two quantities. Three: parsePlainReview hardcodes confidence_score: 0 on every finding it parses (TranscriptReview.tsx:102); it isn't rendered today, and mustn't be until it's real.

R5What has to be captured, and when

The row is only trustworthy if it is frozen at start. Resolving the workspace or re-running the branch match at render time would relabel a month-old card with today's answer — the exact failure this is about. reviewer already lives on this entry for the same reason: a review can run somewhere other than its thread's ambient settings, so its context belongs to the artifact.

// packages/shared/src/contracts/normalized-app-server.ts
export type AppServerThreadReviewEntry = {
  ...
  reviewer?: { backend; model?; reasoningEffort? };
  /**
   * Where the review ran, captured when it started. Reviews run in one of a
   * thread's linked directories, so this belongs to the review artifact —
   * resolving it at render time relabels an old card with today's workspace.
   */
  context?: {
    workspacePath: string;      // the cwd already on StartReviewRequest
    projectLabel?: string;      // "PwrAgent"
    repositoryPath?: string;    // set when workspacePath is a worktree
    gitBranch?: string;         // HEAD of THAT workspace; absent on a commit target
    baseBranch?: string;        // so the chip can tell "PR's own base" from an override
    /**
     * The PR open on gitBranch in this workspace at start. null means the
     * branch was checked and had none; absent means there was no branch to
     * check. Never a list — a PR that is not on this branch is not evidence
     * about this diff.
     */
    pullRequest?: PrSummary | null;
  };
};

Stamped in emitManagedReviewStarted (backend-registry.ts), which already resolves the review's workspace. null and absent have to stay distinguishable — they are R3·d and R3·e.
