PwrAgent · Settings → Applications + Git

External programs — one inventory, one row, one trust signal

PwrAgent shells out to four programs it does not ship: an editor, a terminal, git, and gh. Today two of them are configurable on Applications, and the other two are half-configurable on Git — the gh list has working Use buttons, the git list has none at all. Nothing anywhere tells the operator who signed the binary they are about to hand a repository to. This page audits both panes, defines the shared model, and proposes the built design.

01

What is broken today

Six of these were reported from the screenshots; three more surfaced while reading the code behind them. Causes are cited to the file that produces the behaviour.

DefectWhereCause
Apple's git can't be picked Git GitCandidateRow renders every git candidate with disabled and no onUse handler, so the row has nothing to click. Underneath it there is no setting to write to: applications.gh.path exists in config, applications.git.path does not. Selection is hard-wired to "first executable candidate, env override aside" in discoverGitCommands.
Selecting git would not take effect main Every one of the eight git invocations in the main process spawns the bare word "git" and lets PATH decide. The discovery snapshot is display-only — even a correct picker would change a label and nothing else. This is the reason the fix is not a one-line handler.
No signing or notarization signal both Nothing in discovery reads a code signature. The operator cannot tell an Apple-signed system binary from an ad-hoc Homebrew bottle from an unsigned script that happens to be named git and sits earlier on PATH.
CLIs are missing from Applications Applications The pane is titled "Editor & terminal" and lists exactly those two. It is the first place an operator looks for which programs do you run and from where, and it answers half the question.
No icons for git / gh both App rows get a real OS icon via app.getFileIcon; CLI rows get nothing, not even the letter fallback, because GitCandidateRow and GhCandidateRow pass no icon.
Two different row grammars both An application row reads icon · name · path. A CLI row reads path-as-name with the provenance demoted to a chip — so the same primitive presents the primary fact in the title on one pane and in a 10 px chip on the other.
Rows are not clickable both Only the trailing Use button is a hit target. The row looks like a choice and behaves like a label — the reported "clicking the row does nothing" is true on every pane, git is just the case where there is no button either.
A picker with no group semantics both The lists are a div of divs. A screen reader gets buttons labelled "Use" with no indication that they are mutually exclusive, and arrow keys do nothing.
Selected state carries no verb both The selected row shows a green Selected chip in the slot where the other rows show a button. Nothing says this is the one PwrAgent runs, and the same word is also used for editors, terminals and auth profiles with three different meanings.
Root Eight of the nine are the same root cause: the row primitive is shared, the model behind it is not. Applications rows are backed by a persisted preference (preferredEditorId); CLI rows are backed by a discovery snapshot that re-derives selection on every scan. Give both a persisted preference and the row can become one control.
02

The model — four kinds of one thing

An external program is something PwrAgent executes but does not ship. Each one has: a provenance (who put it there), a location, a version, a trust level, and exactly one of the candidates is the one we run. That is a single model with four instances, and it should be a single list.

ProgramUsed forChosen byPersisted as
EditorOpening a worktree from the composer launcherOperator picks one of the detected appsapplications.editor.preferred_id
TerminalOpening a shell in a worktreeOperator picks one of the detected appsapplications.terminal.preferred_id
ghReading PR status for thread chipsOperator picks, else first executableapplications.gh.path
gitWorktrees, branches, stashes, remotes, handoffNobody — first executable wins— nothing —
Fix Add applications.git.path alongside applications.gh.path, feed it into discoverGitCommands as a config-source candidate the same way gh already does, and resolve every main-process git spawn through one getGitCommand() accessor instead of the bare string "git". Precedence stays env → config → first executable, matching gh exactly.
03

Trust — what we can actually prove, and what it costs

Measured on the reporting machine against the exact binaries in the screenshots. codesign -dvvv answers the whole question for a CLI in about 7 ms; a notarization check is only needed for the Developer ID case and costs 0.3–0.6 s, so it is run conditionally.

Binarycodesign saysReads as
/usr/bin/git Authority=macOS Software Signing → Apple Code Signing CA → Apple Root CA. Identifier com.apple.dt.xcode_select.tool-shim-public. Apple-signed system binary. Also a shim — it dispatches to whatever xcode-select points at, which is worth saying out loud.
/opt/homebrew/bin/git flags=0x2(adhoc), Signature=adhoc, TeamIdentifier=not set Ad-hoc signed. Normal and expected for a Homebrew bottle — it is relinked at install, which invalidates any upstream signature.
/opt/homebrew/bin/gh flags=0x20002(adhoc,linker-signed) Ad-hoc, linker-signed. Same story.
Visual Studio Code.app Developer ID Application: Microsoft Corporation (UBF8T346G9), flags=0x10000(runtime), passes -R="notarized" Developer ID + notarized. The strongest third-party signal macOS offers.
Ghostty.app Developer ID Application: Mitchell Hashimoto (24VZTF6M5V), passes -R="notarized" Developer ID + notarized.
Trap Do not use spctl for CLI tools. Measured: spctl -a -t exec /usr/bin/git returns "rejected (the code is valid but does not seem to be an app)" — for Apple's own git. Gatekeeper assessment is an app-launch policy, not a signature reader; wiring it to a chip would paint the most trustworthy binary on the machine red. Use codesign -dvvv to classify, and codesign --verify -R="notarized" --check-notarization only to upgrade a Developer ID result to notarized.

Chip vocabulary

Six levels, ordered by strength. Tone is deliberate: ad-hoc is neutral, not a warning — the overwhelmingly common case on a developer Mac is a Homebrew bottle, and a chip that cries wolf on the default install teaches operators to ignore the chip.

Apple

Apple-signedSigned by Apple's own Software Signing authority. A macOS system binary, part of the signed system volume.

Notarized

Developer ID + notarizedSigned with a Developer ID certificate and accepted by Apple's notary service. Hover shows the team: Microsoft Corporation (UBF8T346G9).

Developer ID

Signed, not notarizedA real Developer ID signature with no notarization ticket. Fine for a locally built tool; unusual for a download.

Ad-hoc

Ad-hoc signedSigned with no identity — integrity only, no origin. Every Homebrew bottle. Neutral tone on purpose.

Unsigned

No signatureA shell script or a stripped binary. Worth a look when it is early on PATH and named git.

Signature invalid

Broken or tamperedcodesign found a signature that does not verify. This is the only level that earns the danger tone.

Cost Signature inspection runs outside discovery, on its own IPC, cached by path + mtime + size, and only for rows a settings pane has on screen. Discovery keeps its current timing; an operator who never opens Settings never pays for a single codesign spawn.

For One home for the choice, one summary for the answer. Change… deep-links straight to the matching Applications section, so the repair path is one click, not a hunt. The Git pane is then only about behaviour: PR polling, auto-dispatch budget, auth scopes, Xcode-license remediation.
Against An operator arriving from a broken-git error has to follow one link before they can act.

Recommendation — Option B

The Git pane is already 975 lines covering PR polling, auto-dispatch budgets, GitHub auth scopes and two discovery pickers. Its centre of gravity is behaviour, not inventory. Moving the pickers out makes both panes describable in one sentence — Applications: which programs, Git: how we use them — and the "Tools in use" strip still answers the question that brings people to the Git pane in the first place.

Option A is a one-prop fallback if that turns out to be wrong: the section component is shared, so re-rendering the full picker on Git is a single line.

07

Interaction and accessibility

  1. 01The list becomes a radiogroup. role="radiogroup" with an aria-label naming the program; each row is a <button role="radio" aria-checked>. That is what makes clicking the row work, and it is the same change that gives a screen reader "Apple, 2.50.1, Apple-signed, radio button, 2 of 2, not selected" instead of an unlabelled "Use".
  2. 02Arrow keys move within the group, Tab leaves it. Roving tabIndex, so a list of five candidates is one tab stop rather than five.
  3. 03No nested interactives. The trailing element is a state chip on the selected row and a label on the others — not a button inside a button. The visible "Use" affordance stays; it stops being a separate hit target.
  4. 04Trust is never colour-only. Every chip carries a glyph and a word. The ad-hoc chip is neutral by design, so it is not carrying meaning through tone in the first place.
  5. 05A trust chip that has not resolved renders nothing, not a spinner or an "Unknown" pill. Signature inspection is asynchronous and the row must not reflow when it lands — the chip slot is reserved at its final width.
  6. 06Selection is announced. Switching git writes config and re-runs discovery; the section header's health summary is the aria-live region that reports the result.
  7. 07An env override disables the group and says so. PWRAGENT_GIT_PATH already wins over config; when it is set the rows are inert with one line explaining why — the same treatment gh gives today.
08

Icons

Both marks follow the pattern already used for Slack, Discord, Telegram, Mattermost, Feishu and Line: the official file lands under renderer/src/assets/<brand>/ with a README recording its source and usage rules, and renders through an <img> so surrounding CSS colour state cannot recolour it.

MarkForSource and terms
Git git The Git logo by Jason Long, from git-scm.com/downloads/logos, licensed CC BY 3.0. Attribution goes in the asset README next to the file, matching how the other brand assets record their terms.
GitHub gh The GitHub mark from github.com/logos. Not the GitHub Desktop icon — gh is GitHub's own CLI and is not part of GitHub Desktop, so the GitHub mark is both the accurate identity and the one GitHub's brand guidance covers for referring to GitHub.
Fallback Neither asset is required for the feature to work. If a mark is unavailable the row falls back to the same monogram chain AppIcon already implements, so icon licensing never blocks the picker.
09

Build order

  1. 01Make git selectable for real. applications.git.path in config → discoverGitCommands({ configuredCommand }) → resolveGitCommandPreference() → a single getGitCommand() that all eight main-process spawn sites call. Without this step the picker is decoration.
  2. 02Manual path picker for git, mirroring settings:pick-gh-command, including the "did it answer --version" validation.
  3. 03Code signature service. Own module, own IPC, cached by path+mtime+size, codesign on macOS and Get-AuthenticodeSignature on Windows, nothing on Linux.
  4. 04Row primitive gains selection. onSelect renders the row as a radio; existing onUse callers are untouched.
  5. 05One shared section component for a program and its candidates, rendered by Applications for all four programs.
  6. 06Git pane reduces to behaviour plus the tools-in-use strip with deep links.
  7. 07Brand assets for git and GitHub, with READMEs.
