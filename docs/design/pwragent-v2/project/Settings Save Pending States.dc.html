Rules — how a field opts in

Pending is per action, not per panel. useDesktopSettings exposes one saving boolean for the whole pane, so a control cannot learn from it whether it was the one actuated. Each field awaits the promise its own handler returns instead.

Handlers return their promise. onChange is typed => Promise<unknown>, so a fire-and-forget void save(…) is a type error rather than a control that silently never shows pending.

It clears on failure too. A ring left spinning after a rejected write reads as a save still running.

Only narrow controls opt in. Passing pending to SettingsField lays the control out on a row with the indicator to its right. A full-width input has no room, so it does not opt in — text fields save on blur, where the operator has already moved on.

No standing announcer. The role="status" region mounts only while the write is out. A pane holds dozens of these fields, and dozens of idle live regions is the worse trade.

Provenance

Split out of the Connect Slack UX review. Finding B3 there was the same defect one level down — a shared busy flag putting a pending label on the wrong button. This generalises the per-action fix to every Settings field.

Verified against the real MessagingSettings component in headless Chromium: one indicator and one aria-busy element per save, both themes, and zero axe violations under the WCAG 2.0/2.1/2.2 AA rule set the E2E gate uses.
