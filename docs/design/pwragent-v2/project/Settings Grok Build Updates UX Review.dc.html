PwrAgent · Settings → AI Providers → Grok

Two Grok build channels, one word for both — name it, check it, install it

This pane can be running a binary that PwrAgent itself downloaded, checksummed, signature-checked and installed from pwrdrvr/grok-build — and it says nothing about it. No installed tag, no last-checked time, no “a newer build exists”, no check button, no install button. The only control that actually runs a release check is labelled Refresh and described as re-running discovery. Meanwhile the one notice this provider can raise is written for the other channel — an xAI install updated from x.ai/build — and titles itself “Grok update available” without ever saying which Grok.

Provenance The managed channel shipped with main/acp/grok-managed-runtime.ts; the notice is renderer/features/notifications/GrokCliUpdateNotice.tsx; the predicate that decides which channel a runtime belongs to is isPwrAgentOwnedGrokRuntime in main/acp/grok-cli-update.ts. As of this review the newest published pwrdrvr/grok-build release is pwragent-v1.0.4-pwragent.2 (2026‑08‑16), which is also MANAGED_GROK_MINIMUM_SIGNED_TAG — so a machine on that tag is current, and any “update available” it is shown today came from the xAI updater.
01

Two channels wearing one name

Every confusion on this screen comes from the same root: “Grok” is two different products here, with different publishers, different version strings, different release pages and different updaters. Exactly one of them is live at a time — whichever binary the pane marks Using. The pane and the notices currently speak neither channel’s language; they speak a generic one that fits both and identifies neither.

PwrAgent buildxAI build
Published by PwrDrvr — pwrdrvr/grok-build, a downstream fork build xAI — the official CLI
Lives at ~/.pwragent/agents/grok/versions/<tag>/grok, or inside the app bundle ~/.grok/bin/grok or anywhere on PATH
Version looks like 1.0.4-pwragent.2 1.0.5
Updated by PwrAgent — GitHub releases API, SHA256SUMS, platform-signature check, install under versions/ The vendor — grok update --check --json, operator downloads from x.ai/build

Check cadence once per Electron process in dev, at most once per 24 h packaged, forced by the pane’s Refresh 24 h success TTL / 1 h failure TTL, in the background
Rule The runtime in effect owns the update story. If the active binary is a PwrAgent build, the operator only ever sees PwrAgent-build tags, a PwrAgent-build release link and a PwrAgent-build install action. If it is an xAI install, they only ever see xAI versions and x.ai/build. Never both, never one described in the other’s vocabulary. The code already believes this — the comment on refreshGrokUpdateStatusInBackground says so in as many words. The predicate underneath it just isn’t strong enough to hold the line (§02, finding 5).
02

What is broken today

Nine findings. The first four are visible on the reported screen; the rest surfaced reading the code that produces it. Causes cite the file responsible.

DefectWhereCause
The installed PwrAgent build is never named AcpAgentsSettings The PwrAgent build row is a bare toggle plus a paragraph about what the feature does. Which tag is installed, when PwrAgent last checked, and whether a newer one exists are all absent. The tag is legible only by reading the version directory out of a 78-character path string in the row below.
There is no check-for-updates control ipc/settings.ts:532 There is one, disguised: Refresh in the Re-probe row passes force: true, which becomes checkMode: "force" and runs the real release check. Its label reads “Re-run discovery for enabled agents (versions, installs, capabilities).” The only control that updates Grok is documented as a rescan.
The install runs invisibly and reports nothing grok-managed-runtime.ts That same click can fetch a 50–130 MB archive, verify SHA256SUMS, verify a platform signature and swap the active version directory. There is no progress, no “installed pwragent-v…” result, and no error surface: failure is a managedGrokLog.warn and a silent fall back to the cached build.
Use on a PwrAgent build freezes it forever AcpAgentsSettings onUse calls commitPath(instance.command), writing the version-specific path as a manual override — and an override beats everything in resolveActiveAcpInstance. The reported machine is pinned to versions/pwragent-v1.0.4-pwragent.2/grok. When a newer tag publishes, PwrAgent will download it and keep launching the old one, indefinitely, with no indication. The override was never needed: with managed builds on, discovery splices the managed instance ahead of every PATH install, so it already wins.
A pinned PwrAgent build stops counting as one grok-cli-update.ts:39 Channel ownership is decided by GROK_INSTALLER=pwragent, and discovery stamps that only when active.command is string-equal to the command this run’s release check resolved. Pin an older managed version — or let the check fail with no cache, or turn the toggle off while an override still points into versions/ — and the identical binary silently changes channel. The xAI updater is then run against a PwrAgent build and its answer is shown to the operator. This is the mechanism behind the reported toast.
The notice does not name its channel buildGrokCliUpdateNotice Title: Grok update available. Message: Grok 1.0.5 is available; 1.0.4-pwragent.2 is installed. Both are “Grok versions”; neither says whose. A reader holding a PwrAgent build cannot tell whether they are being told about their build or about a different product.
The PwrAgent channel has no notice at all features/notifications/ There is no counterpart to GrokCliUpdateNotice for pwrdrvr/grok-build. The channel PwrAgent fully controls is the one it never reports on — not when it installs a build, not when a pin is holding an old one back, not when a check fails.
Detected paths do not distinguish the channels SettingsPathRow Chips are override/path, a version, and available. Two rows, two different products, one vocabulary. The only channel signal is whether the operator recognises .pwragent/agents/grok inside the path.
x.ai/build is the only release link that exists GROK_BUILD_UPDATE_URL Correct for the xAI channel. Wrong for a PwrAgent build, whose release notes live at github.com/pwrdrvr/grok-build/releases/tag/<tag> and whose update is not something the operator downloads by hand at all.

04

Proposed — the build row becomes the update surface

One new idea, applied consistently: the PwrAgent build row stops being a feature switch and becomes a channel status block — installed tag, last check, state, and the two verbs that follow from it. Everything else on the pane is edited, not added: path rows gain a channel chip, the Manual path row learns to say when it is pinning, and Re-probe stops being the secret updater.

Cadence An operator on the PwrAgent channel who is not pinned should never be asked to install anything — PwrAgent installs it itself within the check window. That is why the middle notice is a transient result, not a durable request: it answers “what changed?” and gets out of the way. 07

The build

Ordered so the correctness fix lands first — items 1 and 2 alone stop the wrong toast, without any new UI.

  1. 1Decide channel by provenance, not by string equality. isPwrAgentOwnedGrokRuntime must be true for any command under the managed agents/grok/versions/ root or inside the app bundle — not only for the exact command this run’s release check resolved. Stamp GROK_INSTALLER=pwragent on that basis in acp-instance-discovery.ts. Fixes findings 5 and, with it, the reported toast.
  2. 2Name the channel in every notice. Split buildGrokCliUpdateNotice into an xAI notice and a PwrAgent-build notice; put the channel in the title; route the release link per channel — x.ai/build for xAI, github.com/pwrdrvr/grok-build/releases/tag/<tag> for PwrAgent builds.
  3. 3Surface the managed metadata over IPC. The install already records tag, checkedAt and installedAt; add a managed-build block to the Grok settings entry carrying installed tag, newest known tag, checked-at, and the last check error. No new network call.
  4. 4Build the status block and its two verbs. Check for updates forces a managed release check on its own, rather than riding inside Refresh; Use newest build appears only when a newer verified build is installed and something is holding it back.
  5. 5Chip the channel on every detected path. PwrAgent build / xAI build, plus newest / pinned for managed versions. Show every installed managed version, not just the active one.
  6. 6Make the Manual path row admit when it is pinning. When the saved override resolves inside the managed versions root, say that newer builds will download and never run, and offer the one-click way out.
  7. 7Re-label Re-probe. It keeps forcing discovery; it stops being the only way to check for a Grok release, and its sub-line points at the control that is.
  8. 8Decision 1 — should Use on a managed row write a path override at all? It is what creates the trap: with managed builds on, the managed instance already wins without an override, so the override adds nothing and freezes the version. The clean fix is for Use on the newest managed row to clear the override rather than write one. That changes existing behaviour for anyone who used it deliberately as a pin — hence a decision, not a checkbox. Recommended: change it, and keep the Manual path field as the explicit, labelled way to pin.
  9. 9Decision 2 — does the PwrAgent channel get a durable notice at all? The pane banner may be enough, and the app already avoids nagging about things it fixes itself. Recommended: yes, but only for the pinned-and-stale case, once per new tag, snoozeable — that is the one state that never resolves on its own.
  10. 10Decision 3 — should a managed install be announced when it succeeds? Today an operator’s Grok binary can change underneath them with no record anywhere in the UI. Recommended: yes, as the transient success notice in §06 — cheap, auto-dismissing, and the only place “what changed?” is ever answered.
