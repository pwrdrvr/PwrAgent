0Brief: agents build stacks, so PwrAgent has to operate them across threads

Harold asked whether PwrGit or PwrAgent ever built stacked-PR GUI and operation support. Neither did. PwrGit’s design is done (PwrGit #646): gh stack’s catalog is the state, git replay + merge-tree plan, one update-ref transaction applies. PwrAgent has a harder version of the problem. Agents create, extend, restack, reorder, submit and sync stacks. Each layer usually lives in a different thread, with its own worktree, and that thread’s agent may be mid-turn when the stack below it moves. So this board is about who runs the engine, how a stack maps onto threads, how a running agent is asked before its branch moves, and what it’s told afterwards. Everything here is a proposal. Nothing is built. Repository names, branches, PR numbers and shas are invented.

0aWhat PwrAgent already has to build on
1

Stack order inference exists, for combined reviews

pullRequestStackOrder() (packages/shared/src/pull-request-review.ts) walks base→head and returns members bottom-first, or nothing for a fork, cycle or gap. It has a property test. Today only the Composer’s “review together” uses it.

2

Thread dependencies already hold merges

manage_thread_dependencies has pr_merged and merge_build, and holdMerge makes merge_pull_request throw merge_held through assertMergeNotHeld, re-read just before the provider write. That is half of “merge a stack bottom-up”.

3

Turn queues already hold for reasons

ThreadTurnQueue (owner-core) keeps a set of hold reasons per thread, and move_thread_workspace already waits for the turn to end, acts, then starts a continuation. That’s the shape of the restack handshake.

4

Forge writes have policy, RBAC and merge-queue routing

FORGE_AGENT_WRITE_TOOL_GROUPS gates every write by project and agent (allow · auto · ask · off), messaging RBAC maps them to tools.forge_write, and merge_pull_request enqueues when a queue is required.

0bWhat goes wrong today when an agent stacks
1

An agent can only rebase its own worktree

When the bottom layer takes a review fix, the agent there can’t move the branches above it. They are checked out in other threads’ worktrees, and git rebase --update-refs silently skips refs checked out elsewhere. Every layer’s PR quietly shows the parent’s old commits.

2

Merging strands the layer above

After a parent merges, the layer above is still based on the parent’s branch, and nothing in PwrAgent retargets it. Whether GitHub retargets it or closes it when that branch is deleted depends on how and when the branch goes: an agent’s git push --delete, repository auto-delete, or a GitHub stack that owns the bases.

3

Auto-merge on a middle layer merges into its parent

merge_pull_request turns on auto-merge while checks are pending under a merge queue. On a layer whose base isn’t trunk, that merges into the parent branch, not into main. gh stack disables auto-merge on stacked PRs for this reason.

4

Nothing shows a stack

No n/N chip exists. The PR rail sorts by number, and the Star Map draws only federation links. A four-thread stack looks like four unrelated threads.

1Who runs the engine: PwrAgent keeps its own copy

The stack engine covers squash boundaries, patch-id proofs, ref transactions and worktree follow. It runs to a few thousand lines, which is too small to justify a shared library that both apps would have to publish, version and release in step. So PwrAgent copies PwrGit’s engine design into its own owner, and owns that copy. The three tools interoperate through files on disk, never through calls. Today PwrAgent’s main process never calls a pwrgit_* tool. PwrGitConnectionService only relays PwrGit’s tools to agents.

1bWhere each piece lives

Layering. The engine copy lives in packages/owner-core, which already holds host-independent owner services. A runGitCommand-backed GitRunner adapter lives in apps/desktop main, next to the bundled Git (2.56.1, so git replay is there everywhere). The renderer imports only @pwragent/shared: health and inference are pure functions there, and everything else reaches the renderer over IPC.

2Threads and stacks: a layer is a thread, the catalog is the truth, the tray is a projection

There are two ways to map threads onto stacks. In the first, one thread owns the whole stack and checks layers out in turn. In the second, each layer is a thread with its own worktree, branch and PR. PwrAgent’s per-thread PR automation, watches, review and Continue After all key on the thread that holds a PR, and agents work layers in parallel. So the unit is the layer thread. One thread may still hold several layers that aren’t checked out anywhere, while it writes them in order.

2bSub-threads: the tray mirrors the stack, but a drag only stages a plan
1

New layers are born as sub-threads of the lead

add_branch with newThread: true creates the layer thread with parentThreadId = lead. PwrAgent writes subthreadOrder top-first, so the tray reads like GitHub’s stack, trunk last.

2

Adopt doesn’t reparent

Adopting four existing threads leaves the sidebar alone. Parentage is the operator’s grouping (“UI-only”, per navigation.ts). The stack shows up through chips and the spine wherever the rows already are. Group as stack is an explicit, separate action.

3

Dragging a layer row inside a stack tray plans a reorder

The held card says Plan reorder instead of moving the row. On drop, PwrAgent stages the reorder plan with its live forecast, and the rows snap back to catalog order until the plan is applied. Escape cancels as usual. Dropping a row outside the tray detaches the sub-thread and leaves the stack untouched.

4

A stack belongs to one clone

Its owner is the instance whose $GIT_COMMON_DIR holds the catalog. A layer thread handed off to another machine keeps its PR, but leaves that clone’s worktree. It shows as remote · read-only, and plans that would move its branch are refused until it comes home or pushes.

4Live: agents operate one stack across four threads

Four threads, one per layer, and a lead thread that coordinates. Two layer agents are mid-turn. Push a review fix to the bottom, and the lead restacks: PwrAgent plans, holds each affected thread at its next safe point, re-plans, moves every ref in one transaction, and tells each moved thread what changed under it. Then Submit, which needs your approval because it publishes. Then merge #651 on GitHub and watch the automatic sync. Click a thread row to read the notice it received. Race makes the Scheduler agent commit before its turn ends, so the compare-and-swap refuses the stale plan. Conflict routes the fix to the thread that owns the conflicting layer. Motion: cards re-seat in 360ms on ease-out. The amber line marks the branch being replayed. A restacked wire draws solid. Running threads carry the thinking scanner. Under reduced motion all of it stops, except the scanner, which parks mid-sweep, as desktop-style-guide.md requires.

5The handshake: never move a worktree under a running turn

An agent mid-turn holds a model of its worktree: files it read, a test it’s about to run, a commit it’s composing. Moving HEAD under it would invalidate that model with no warning. So the apply runs in a fixed order: plan → hold → re-plan → compare-and-swap → move → notify → release. A thread counts as running when isThreadActive is true: an active turn, an active sub-agent, a background task, or a pending approval or input request. Background tasks count because they write to the worktree too.

6bThe existing PR tools learn about stacks additively
1

create_pull_request keeps its contract

base still defaults to the default branch. Changing that default would change a field’s meaning. When head is a stack layer, the result gains stack: { name, position, expectedBase, drift }, and the catalog records the PR under the lock. Its description points agents at submit for a whole stack.

2

update_pull_request base changes are shown as drift

A base that disagrees with the catalog still goes through. The result gains stack.drift: true, and every layer view shows GitHub base ≠ stack. When a GitHub stack owns the bases, PwrAgent refuses with stack_owns_base, because GitHub would revert it.

3

merge_pull_request gets a stack guard beside merge_held

assertCanMerge adds stack_parent_open. A layer merges only when every layer below it has merged and its GitHub base is trunk. That also covers the queue path: auto-merge is never turned on for a PR whose base isn’t trunk. These guards fix today’s footguns, so they ship in P0, before any engine.

4

Policy and RBAC reuse the forge gate

FORGE_AGENT_WRITE_TOOL_GROUPS gains stacks (default auto) and stack_publish (default ask). The group is chosen per call from the plan, as forgePrToolGroup already does for approving reviews. Messaging turns map to tools.forge_write through isForgeWriteToolName. An operator rule stack_publish = allow for one project and agent is the standing grant. That’s the operator’s call, not a hard-coded “never”.

7Automation: thread dependencies drive sync, and merges walk the stack bottom-up

Stack automation is Continue After with a structured continuation. Creating or adopting a stack arms one dependency per layer above the bottom. The waiting thread is layer k. The condition is pr_merged on layer k−1’s thread, pinned to that PR’s URL, with holdMerge: true and automatic: true. When it fires, ThreadDependencyCoordinator passes a stack:sync continuation to the stack coordinator instead of a plain wake prompt. The thread is woken only after the sync, with the notice.

7aMerging a whole stack: two regimes

When the stack is linked on GitHub, it uses gh stack’s own path (v0.3.0 merge.go): merge-async up to the chosen PR, merge-queue aware. Otherwise PwrAgent walks the chain itself, and every step is a mechanism that already exists: merge_pull_request, pr_merged, the sync, then ci_passed. A merge_build condition instead of pr_merged makes the layer above wait for main’s post-merge build before it restacks onto it, per project.

8When it goes wrong across threads

Every failure path has the same two guarantees. Nothing moves until everything can move: the forecast is merge-tree, and the apply is one update-ref transaction against expected tips. The thread that owns the problem is the one asked to fix it.

1

A conflict in another thread’s layer

The plan stops before that layer. Options: apply only the clean layers below; route the conflict to the owning thread with send_message_to_thread (conflicting commit, files, and the parent change), which resolves it with a real rebase --onto in its own worktree and calls manage_stack_operation continue, after which the rest is re-planned from its tip; or abort. If the owner is archived, the lead resolves it in a disposable worktree.

2

Two agents racing on one stack

Applies serialize on the existing per-common-dir PerKeyAsyncLock (the key worktreeMutationLocks uses), then compare-and-swap in update-ref. The loser gets stale_plan with the refs that moved. A re-plan whose forecast is unchanged applies once on its own. One whose forecast changed goes back to the caller.

3

gh stack or PwrGit is mid-operation

A gh-stack-rebase-state, -modify-state or -migration journal, PwrGit’s pwrgit-stack-op.json, or a contended gh-stack-operation.lock, refuses with gh_stack_busy and names the tool and the worktree. PwrAgent never breaks a flock and never deletes a journal. The operation lock is held only from re-plan to catalog write: milliseconds, never a turn.

4

The remote moved

If the local tip is an ancestor of the remote one (a reviewer pushed a suggestion), the plan fast-forwards first and the worktree follows. If they really diverged, it’s remote_diverged. Leases never push over it. The layer thread is asked to integrate the remote commits, because it’s the one that knows them.

5

The lease fails at push time

--atomic means none of the branches moved on GitHub. PwrAgent re-fetches and re-plans. Local refs are already correct, so only the push steps are retried, and with a new approval if the push list changed.

6

PwrAgent quits mid-operation

The engine’s journal (pwragent-stack-op.json) records the phase. On restart, the coordinator releases holds for an operation that hadn’t reached the transaction. After the transaction, it re-sends notices, which are idempotent by opId, and then releases. Holds are journalled with the operation, so a crash can’t leave a thread held forever.
