MCP servers — say which Codex, show the tools, name the state

The pane lists the MCP servers of one Codex profile and gives the operator two verbs: Relogin and Remove. It counts 206 tools and shows none of them; it prints the OAuth mechanism where the operator is looking for a state; and it never says the one thing that explains every surprise on this screen — that these servers and their sign-ins belong to ~/.codex/profiles/work and not to the ~/.codex that a codex run outside PwrAgent uses. This page audits the pane, corrects the model behind it, and proposes the build.

Provenance This pane is not from #1900. It shipped in #1495 feat(desktop): manage Codex MCP servers in Settings, with #1886 adding the unknown auth status. #1900 (prefer managed CLIs in integrated terminals) touches no MCP code; it makes an integrated terminal's codex the managed binary, pairing with the CODEX_HOME that terminal already exports. See §02.

02

The model — two axes, and only one of them moves credentials

The brief for this review assumed MCP sign-ins are separated because PwrAgent runs a custom Codex build. They are separated, but the custom build is not what does it. Getting this right changes the copy, so it is worth stating exactly.

AxisWhat it selectsWhere it comes fromMoves MCP credentials?
Codex profile The CODEX_HOME every Codex process is given — and therefore config.toml, auth.json and each MCP server's stored OAuth credentials. discoverCodexAuthProfiles. System default resolves to ~/.codex; every named profile resolves to ~/.codex/profiles/<name> — resolveCodexProfileRoot joins "profiles" unconditionally. Yes. This is the whole mechanism.
Codex build Which binary runs — PwrAgent's managed build from pwrdrvr/codex (required by Token Miser) or a Codex the operator installed themselves. codex-managed-runtime.ts, tags pwragent-v*, signature-verified and pinned. No. Both builds read whatever CODEX_HOME they are handed. A managed build on ~/.codex sees exactly the sign-ins a stock build sees there.
So The honest sentence for the UI is “these sign-ins belong to this Codex profile” — not “to PwrAgent's Codex”. On the screenshot's work profile the split is real and total: ~/.codex/profiles/work/config.toml is a different file from ~/.codex/config.toml, Codex does not merge them, and an OAuth login performed against one is invisible to the other. On System default there is no split at all — PwrAgent and a bare codex share one store, and a second list would show the same twelve rows twice.
Already handled Integrated terminals do export the selected profile's CODEX_HOME. Every path through resolveTerminalSpawnEnvAsync runs withStartupCodexHome, which sets it from startupCodexHome — resolveCodexHomeForProfile(config.models.codex.profile), on main since #1227 and untouched by #1900. So a codex typed in a PwrAgent terminal already agrees with the app on which store, and #1900 makes it agree on which binary too. The gap this pane has to explain is therefore only ever with a Codex run outside PwrAgent — the operator's own terminal app, an editor, any other tool — which falls back to ~/.codex.
03

Sign-in vocabulary — five states, one wording, both surfaces

The protocol gives five values. Each one should render as a state the operator is in, in the same words on the Settings pane and in the thread rail. One exported formatMcpAuthStatus in @pwragent/shared, imported by both, so the two cannot drift again.

Signed in

oAuthCodex holds OAuth credentials for this server. Hover: “Signed in with OAuth. PwrAgent proves this when the server next starts.” was “OAuth” / “OAuth”

Signed in · token

bearerTokenA static bearer token is configured. Same healthy tone as OAuth — it is a working credential, just not an interactive one. was “Bearer token” / “Bearer token”

Sign-in required

notLoggedInThe one state that needs the operator. It is the only state that earns a warning tone, and the only one that promotes Sign in into the collapsed row. was “Login required” / “Sign-in required”

No sign-in needed

unsupportedThe server authenticates nobody. Neutral, and phrased so it cannot be read as a failure — this is the majority state on the reported screen. was “No login” / “No authentication”

Sign-in state unknown

unknownThe Codex build did not report one (#1886 added this so an older build degrades instead of throwing). Muted, not alarming — it describes our ignorance, not the server's health. was “Authentication unknown” / same

Failed to start

startupStatus: "failed"A separate axis from sign-in, and the only one that earns the danger tone. It carries startupError inline. Today this renders as the bare lowercase word failed.

Honesty “Signed in” is a statement about stored credentials, not a live probe — the protocol reports what Codex holds, and an expired refresh token still reads as oAuth until a start attempt fails. That is why the health dot is driven by startupStatus and the chip by authStatus: the pane shows a credential and a proof, and never lets one impersonate the other.

The second list — what it would take

The ask: show the operator both their PwrAgent-profile MCP servers and the ones in the Codex they use outside PwrAgent, so the split stops being a surprise. The design is a scope switch above the list. The cost is in the second tab, and it is not small.

Cost Every fact on the first tab — tool lists, sign-in state, startup health — comes from this.codexClient.listMcpServers(), the one running app-server process, bound to one CODEX_HOME. There is no second client, and the repository's Codex data boundary forbids reading ~/.codex/config.toml to fake one. Filling the second tab with real state means spawning a second Codex app-server against ~/.codex — which starts that profile's MCP servers, with their subprocesses and network calls, as a side effect of opening a settings pane.

Decision 1 — how much of the second list do we build? Answered: B

Three answers, cheapest first. The mockup above shows the chosen one. All three are compatible with everything in §01–§05, which is why that work does not wait on this.

A — Tell, don't show

No second tab. The scope banner's third line does the whole job. Zero new process cost, ships with the rest, and kills the surprise even though it never shows the other list. Hidden when the selected profile is System default, where there is nothing to warn about.

B — Second tab, names only, on demand (chosen)

The tab appears only for a named profile. Nothing loads until the operator clicks it. It lists server names only, every row explicitly not inspected, with actions disabled and a line saying sign in from your own Codex. Answers “did my work profile miss servers I set up?” — the actual question — without starting anything. Needs a names-only source that respects the data boundary: a protocol call scoped to a given CODEX_HOME, or a narrowly authorized config read added to check-codex-storage-boundary.mjs the way the rollout-repair module was. That authorization is a PwrDrvr call, not an implementation detail.

C — Second tab, fully live

Spawn a second app-server against ~/.codex behind an explicit Inspect button, and get real tools, sign-in state and health — plus working Sign in for that store. Strictly the best answer and strictly the most expensive: a second Codex process, that profile's MCP servers all started, and a second lifecycle to own. Worth it only if operators are expected to manage both stores from here rather than understand the split.

07

Build order

Steps 1–7 are the pane the screenshots asked for and are independent of the second list. Step 8 is Decision 1's implementation, answered B, and is gated on the boundary question inside it.

  1. 1One vocabulary. Export formatMcpAuthStatus from @pwragent/shared with the §03 wording; delete both local copies in PluginsSettings and McpInventoryPanel. A test asserts all five values, so a sixth protocol value cannot ship as a silent blank.
  2. 2Show the tools. Lift InventoryLine out of McpInventoryPanel into a shared component and put it in a row drawer. No contract change — the array is already fetched.
  3. 3Split credential from proof. Health dot from startupStatus, chip from authStatus, and never collapse the two. Give startupStatus: "failed" the danger tone and its startupError inline.
  4. 4Disambiguate zero. A ready server with no tools says no tools published; a server that never started says why. Requires keeping the pane subscribed to mcpServer/startupStatus/updated from mount, not only while an action is pending.
  5. 5Rebuild the row. Dot, chevron, name, tool count, chip, one verb. Remove into the overflow; Sign in filled only where notLoggedIn.
  6. 6Health in the header. 12 servers · 206 tools with ready / need-sign-in / failed counts, replacing 12 configured.
  7. 7The scope banner. Profile name and CODEX_HOME, the managed Codex build and version from snapshot.runtime.tokenMiser.managedCodex, and the outside-PwrAgent sentence — suppressed on System default. Plus the filter, and the Collapse/Expand cleanup.
  8. 8The second list (B). On-demand, names-only System default tab, shown only for a named profile. Blocked on choosing its boundary-safe source: a CODEX_HOME-scoped protocol call, or an explicit PwrDrvr authorization for a names-only config.toml read in check-codex-storage-boundary.mjs.
