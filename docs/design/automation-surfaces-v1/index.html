Six surfaces from the Automations editor, each shown as it behaves on fix/automation-provider-surfaces (left) and as this pass proposes it should read (right). Tokens and control geometry are transcribed from apps/desktop/src/renderer/src/styles/app.css. Append ?slide=<id> to isolate one sheet.

  1. picker — the DM rows in the surface picker

  5. destination — a Telegram DM destination with a live topic field
  6. replay — the empty state blames the provider for a scope limit

Sheet 2 · Trigger → manual entry

Typing a DM ID builds an automation that never fires

Manual entry always saves conversationKind: "channel". On Slack, Mattermost, Feishu and Discord the matcher rejects a real DM against a channel-kind target, so the automation is silently inert. On Telegram and LINE a legacy heuristic recognises the raw user ID and it works. Same action, two outcomes, no feedback either way.

The Slack channel ID. In Slack, open the channel details and copy the ID at the bottom, or copy a message link and take the C... segment.

The Slack member ID of the person whose DMs should trigger this — open their profile and copy the member ID. Not the D… conversation ID.

One switch decides the kind, so the saved snapshot carries recipientUserId and the matcher can agree with the form. Label, placeholder and hint all follow the switch, so the field asks for the identifier it will actually use.

Sheet 3 · Trigger → Discord

A picker that promises channels it can never list

Discord's only authorized list is of guilds, which are servers rather than conversations, so the editor offers DMs and nothing else. Every noun around the control still says “channel”, and the “Authorized channels” heading never renders. Three of six providers also get no manual-entry guidance at all.

Sheet 4 · Filters → preview

History support is known before the operator asks for it

The main process decides historySupported synchronously from the provider and the scope. The editor only learns it after the panel opens, and because the flag starts false the panel asserts “History is unavailable” for a frame before the answer arrives. It also calls the trigger source a “destination”, which is a different field later in the same form.

Sheet 6 · Automations list → replay

The empty state now blames the wrong thing

listReplayCandidates gained two new refusals in this change: a trigger with a recipientUserId or a parentId. The copy underneath was written when the only refusal was the provider, and it still says so — which for a Slack DM trigger is simply false.

On the branch — Slack DM trigger

Replay a recent message from the trigger conversation. The badge is the filter's live verdict — replaying a non-matching message is a way to test what the automation would do if the filter let it through.

This provider can't serve conversation history, so there is nothing to replay. Use “Preview live messages” in the editor to test against new traffic instead.

Slack does serve conversation history — this same automation would offer replay if its trigger were the #release-eng channel. It is the DM scope that this build cannot read, and the sentence sends the operator to check the wrong thing.

Proposed — one sentence per refusal

Contact DM trigger — PwrAgent can't read back a contact's DM history, only a channel's. Use “Preview live messages” in the editor to test against new traffic.

Thread or topic trigger — replay reads whole conversations, not a single thread. Use “Preview live messages” in the editor to test against new traffic.

Provider without history — Telegram can't serve conversation history, so there is nothing to replay. Use “Preview live messages” in the editor to test against new traffic.

The refusal reason already exists in the main process; only supported: false survives the IPC. Widening that to a reason code lets each sentence name the real constraint and keeps the provider sentence true when it is the one that applies.
